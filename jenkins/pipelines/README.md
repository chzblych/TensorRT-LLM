# L0 pipeline modules

`L0_MergeRequest.groovy` and `L0_Test.groovy` own job input resolution and
Declarative stage ordering. Functional code, defaults and tests live with the
feature that owns them. Keep every affected source file within 1000 lines;
CPS-generated bytecode may also require splitting a large method earlier.

| Location | Responsibility |
| --- | --- |
| `../pipeline-library/src/trtllm/ci/pods/` | Shared Pod rendering, role/platform profiles and defaults |
| `../pipeline-library/src/trtllm/ci/parameters/` | Read-only parent/child parameter names and filter parsing/defaults |
| `../pipeline-library/src/trtllm/ci/stages/` | Pure stage-family expansion and validation |
| `../pipeline-library/src/trtllm/ci/results/` | Parent result collection, available even if preparation fails |
| `common/` | Artifact paths and stage-pattern helpers |
| `mr/` | Change analysis, selection, CBTS, preparation and child-job orchestration |
| `test/` | Test planning, executor adapters, artifacts, reporting and infrastructure lifecycle |
| `tests/` | Offline behavioral tests and baseline-derived output checks |

## Loading and dependencies

The entries load the repository-local library before agent allocation with
Jenkins' native `library` step. The explicit
`legacySCM(scm: scm, libraryPath: 'jenkins/pipeline-library')` retriever uses the
job's existing Pipeline-from-SCM configuration. It needs no global library
registration or separate repository. The identifier follows the job's commit/ref
inputs; the retriever's SCM selects the actual source. Existing floating SCM
refs retain their existing resolution semantics.

Pod construction and unconditional parent result collection can therefore run
before functional scripts have a workspace. The Pod adapters in the entries only
resolve Bloom GPU identities and generated labels. Rendering is pure; MR agent
resources, Test resources, driver selection, ARM storage and ModelExpress
behavior keep their existing profiles. Timeout overrides are explicit inputs.

The MR entry loads functional scripts after its existing checkout resolves
`env.gitlabCommit`. The Test entry uses a sparse checkout of `jenkins/pipelines`
at its supplied commit. Scripts return their instance through `load` and accept
explicit initialization inputs. Both loading paths must match the job source.

`runParameters` contains read-only wire keys. Its parent and child filter
methods return fresh data and retain their different defaults, including old
boolean/string/null behavior. Build owns its build-job and Kitmaker defaults;
execution modules receive the Pod defaults they actually use. Avoid storing
method temporaries on the Pipeline object. Image maps, build arguments, rerun
counts, runners and stage-planning maps are local and returned explicitly.
Module-owned `@Field` state uses direct `this.@field` reads and writes: ordinary
Script property assignments in CPS can target the shared Binding. Instance
options, context references and catalog data must remain on their own module.

## Stage definitions and shards

`test/stages.json` is the single catalog consumed by both Groovy execution and
the Python stage-mapping/CBTS readers. Define a test family once:

```json
{
  "name": "A10-PyTorch-{shard}",
  "platform": "a10",
  "testList": "l0_a10",
  "splits": 3
}
```

Within its architecture/runner group this expands to `A10-PyTorch-1`, `-2` and
`-3`, with the matching split index and total. Groups define `name`, `arch`
(`x86` or `sbsa`), `runner` and `stages`. Families may specify GPU/node counts,
a runner override and the existing execution options. The explicit runner is
`kubernetes`, `slurmAgent` or `sbatch`; multi-node Slurm stages use `sbatch` even
when the legacy `runWithSbatch` tuple flag is false. Validation rejects duplicate
names, invalid shard counts and incompatible runner options.

The catalog retains all 156 runtime stages and their order. Of those, 33 were
previously generated dynamically and invisible to the Python regex readers.
They retain `discoverable: false` to preserve the existing 123-stage tool view;
changing that visibility is a separate selection-policy change. Explicit legacy
Groovy sources remain supported by the mapping tools.

`Stages.groovy` builds a fresh plan from the expanded catalog and returns
`[jobs: ..., infraScopes: ...]`. The entry owns dispatch, single/multi-GPU
splitting and the shared execution inputs inherited from the parent.

## Three execution paths

| Runner | Allocation | Test execution |
| --- | --- | --- |
| Blossom/Kubernetes | Pod allocation/retry in `Runtime.groovy` | `JenkinsTestRunner.groovy` on a Jenkins executor |
| Slurm Jenkins agent | Slurm allocation, node registration and Docker/Enroot context in `SlurmAgent.groovy` | The same Jenkins test body, with the Slurm-specific attempt adapter |
| Slurm native sbatch | Submission, remote monitoring and cleanup in `SlurmSbatch.groovy` | Generated remote scripts from `SbatchScripts.groovy` |

The first two share test preparation and JUnit preprocessing. The native sbatch
control flow remains separate. Common waive/reuse preparation and artifact/test
command contracts are shared where their behavior is the same. Preserve
runner-specific interruption, retry, timeout and cleanup ordering.

`test/State.groovy` owns the original `GlobalState` Class. Upload guards, runtime
estimates, maintenance records and port allocation still share its static
collections through `ciState`; their persistence/lifecycle semantics are
unchanged. This state is distinct from immutable configuration and call-local
variables.

## Verification

From the repository root with Groovy 2.4 or a compatible runtime:

```sh
for test in jenkins/pipelines/tests/*Test.groovy; do
    groovy "$test" .
done
```

The tests cover baseline Pod/YAML output, input serialization, shard expansion,
runner event ordering, generated shell and interleaved invocation state. Keep
Python discovery metadata and Groovy execution expansion consistent. Offline
CPS compilation and mocked execution do not verify controller approvals, live
SCM retrieval, GPU execution or restart/resume.
